# Implementation status

Implemented: schema migrations, Stellar/EVM event watchers, rail pollers, public REST reads, source-scoped Axelar lookup, confirmed direct ITS payment verification, and optional signed Stellar TTL/claim jobs. The checked-in record names the real Stellar router and no EVM Hyperion deployment.

Removed: mocked gas top-ups, synthetic second-step attestations and receipt-only fabricated inbound deliveries. They must not reappear as advertised capabilities without a verified contract integration.

Network acceptance passed: the current testnet lane was deployed and activated, a real wallet transfer confirmed on Stellar, and matching ITS/token payment events established its Sepolia delivery in the indexer. The API server alone cannot establish background worker availability.

Axelar GMP status is only a candidate signal: a transfer becomes delivered after the configured deployment, source event fields, destination receipt and payment event all match. Axelar ITS admission requires valid deployed service receiver metadata on the selected network. Direct ITS payouts do not require a Hyperion EVM router. Configuration admission is metadata validation; only independently verified matching chain events establish delivery. Generic GMP adapter extensions still require their implemented contracts and signed acceptance before runtime enablement. Signer ownership now uses PostgreSQL advisory locks and committed public submission checkpoints; archived Soroban footprints are restored with the native protocol operation before unchanged maintenance calls. Additional rails/networks still require their own implementation and validation. The complete PostgreSQL-backed suite passes, and the live acceptance proof is preserved in the contracts deployment evidence.

EVM-to-Stellar ITS delivery remains disabled. Enabling it requires the implemented reverse-direction router/callback contracts, validated EVM deployment and token-manager metadata, and independent signed source/destination acceptance. Provider status and adapter custody are not payout evidence; runtime support must bind the EVM source transfer to a canonical Stellar router delivery for the exact encoded recipient, preserving muxed-account identity. Unsupported token-manager mappings remain unverified.

New-lane acceptance is explicit: source indexing, provider discovery, a finalized destination receipt, canonical payment, token, amount and network identity must all be evidenced. Provider status alone never activates a lane; missing prerequisites stay visible for operator review.

Allbridge support is implemented only as a verified adapter lane, never as a status substitution. A configured-validator Ed25519 signature may authenticate a signed source intent, but it is explicitly separate from destination payout proof. Runtime enablement requires the owning contracts issue to supply implemented Allbridge contracts, validated Stellar/EVM deployment metadata, explicit configured validator keys, canonical source and destination payment evidence, independent signed source/destination acceptance, and replay-safe ingestion. The checked-in testnet deployment has no Allbridge adapter and remains disabled until those prerequisites exist.

`evaluateLaneAcceptance` additionally requires independent Ed25519 source and destination reviewer signatures over one domain-separated public payment record. The owning deployment review supplies the two trusted public keys and expected network, chains, token representation and precision. Boolean-only test/provider assertions cannot pass. Reports never modify runtime configuration or enable a candidate lane. Signature validity attests to the reviewers' signed observations; those reviewers still must independently inspect the implemented contracts and canonical payment before signing.

The reusable PostgreSQL concurrency runner uses only `TEST_DATABASE_URL`, never the application's fallback database. Stress tests require a local database whose name identifies a test/session; `HYPERION_ALLOW_REMOTE_CONCURRENCY_TEST_DATABASE=true` is a separate explicit opt-in for a reviewed remote test target. Real transactions cover competing watcher leases, full-width compare-and-swap cursors, deadlock victim rollback and lock-timeout recovery; the existing SQL migration-runner tests also verify contended ownership and failure recovery.

## EVM-origin source-router activation

EVM-origin source indexing remains disabled until the owning contracts repository supplies an implemented and deployed Hyperion source router, validated deployment metadata, its verified initialization block and independent signed source/destination acceptance evidence. Registry presence, provider status or an active destination/provider lane must never create an EVM source watcher or establish destination delivery. Activation metadata must bind the exact chain, router address and revision and preserve full-width identifiers, integer-string amounts and canonical replayable source evidence.

EVM-to-Stellar CCTP delivery remains disabled until implemented inbound contracts, validated deployment metadata and independent signed source/destination acceptance are supplied. Provider status alone is not payout evidence; reverse support must bind source burns to destination message identity and distinguish parked claims from recipient payment. Missing inbound contract capability blocks admission.
